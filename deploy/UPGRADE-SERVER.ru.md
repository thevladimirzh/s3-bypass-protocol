# Обновление сервера до v0.1.0-fork.4

Инструкция для владельца VPS. Скрипт: `deploy/upgrade-server.sh`.

Обновление **не трогает конфиг, ключи и бакет** — ни разу.

---

## Что вообще меняется

Один симптом, который вы видели, и двенадцать причин под ним.

**Главное.** Writer ронял файл после `uploadAttempts`. Читатель идёт строго по
порядку и перескочить пропуск не может — поэтому один потерянный объект
вешал сессию на минуты. Это и есть 15–29-секундные рукопожатия. Релиз
переписывает доставку так, что файл сдаётся бакету, а не сдаётся с первого
раза.

**Остальное найдено аудитом и уже исправлено** (`docs/analysis/server-audit-2026-10-10.md`):

| | Что было | Почему это видно снаружи |
|---|---|---|
| C1 | Паника на коротком имени сессии | Сервер мог упасть целиком |
| C2/C3 | `Close()` зависал; гонка `close(uploadQueue)` | Сессия не закрывалась, паника в логе |
| H1 | AWS SDK молча подменял ошибку своим retry | Настоящая причина сбоя не доезжала никуда |
| H3 | `uploadTimeout` ограничивал всё тело PUT | Крупные файлы не влезали в 8 с |
| H4 | 96 одновременных PUT против пула 48 | Задний план ждал в очереди и триггерил хеджи |
| H5 | Рост внутренних карт сессии | Утечка на длинных сессиях |
| M1 | `SetupWebhook` без таймаута | `Server.Init` мог повиснуть |
| M2 | У `List` не было дедлайна | Замолчавший backend навсегда вешал чтение |
| M3 | `local` неэквивалентен S3 | Объект мог наблюдаться наполовину записанным |
| M4 | Коллизия ID lifecycle-правил | Правила могли отменять друг друга |
| M5 | Один медленный ACK блокировал весь watchLoop | Переставали замечаться новые сессии |
| M6 | `cleanupSession` и удаление файлов молчали | Объекты утекали в бакет навсегда |

## Что понадобится

На VPS: `curl`, `unzip`, `systemctl`. **Go не нужен** — ставится готовый
бинарь из релиза. Права root.

---

## Шаг 1. Посмотреть, что стоит сейчас

```bash
./deploy/upgrade-server.sh --status
```

Покажет путь, версию, digest, состояние юнита и — построчно — какие из
маркеров нового релиза в бинаре есть. Отсутствующие маркеры означают, что
стоит старая сборка. Конфиг, если найден, тоже печатается — но не читается
скриптом.

## Шаг 2. Прогнать вхолостую

```bash
sudo ./deploy/upgrade-server.sh --dry-run
```

Ничего не меняет: печатает, что именно скачает и куда встанет.

## Шаг 3. Обновить

```bash
sudo ./deploy/upgrade-server.sh
```

Скрипт по порядку:

1. скачивает `Xray-linux-64.zip` и `.dgst` релиза;
2. сверяет SHA-256 с опубликованным — несовпадение, стоп;
3. **проверяет маркеры**: строки, которые есть только в этой сборке. Это
   отсекает чужой бинарь, который иначе скачался бы, запустился бы и выглядел
   бы как успех;
4. **`run -test` прогоняет новый бинарь против живого конфига.** Не прошёл —
   стоп до подмены, работающий сервер не тронут;
5. копирует текущий бинарь в `<путь>.bak.<метка>`;
6. ставит новый через `install` + `mv` в том же каталоге — `rename(2)`
   атомарен, юнит не может перезапуститься на полузаписанном файле;
7. перезапускает юнит и **10 секунд следит, что он не упал**. `systemctl
   restart` радостно отчитывается об успехе и для процесса, который стартовал
   и сразу умер — поэтому проверка не ограничивается `is-active`;
8. на любой неудаче откатывается на бэкап и только потом выходит с ошибкой.

Бэкапы: хранятся последние 5 (`--keep N`).

### Если релиз ещё не опубликован

Скрипт требует существующий тег. Проверить:

```bash
gh release view v0.1.0-fork.4 -R thevladimirzh/s3-bypass-protocol
```

## Шаг 4. Проверить под нагрузкой

Это главная часть. «Скрипт отработал» ничего не значит — надо увидеть, что
симптом ушёл.

**Что смотреть.** Подключитесь клиентом и откройте что-нибудь тяжёлое. Раньше
первый запрос после подключения висел 15–29 секунд. Сейчас — секунды.

**Чем подтвердить, что это новая сборка, а не просто повезло.** В журнале
появились строки, которых раньше не было:

```bash
journalctl -u xray-fedarisha -f | grep -E 'read list failed|delete queue full|cleanup:'
```

Их отсутствие — нормально: это диагностика, она молчит, когда всё хорошо.
Поэтому надёжнее проверить бинарь:

```bash
./deploy/upgrade-server.sh --status
```

Там должны быть **все три** маркера. Если написано `MISSING` — стоит старая
сборка, независимо от того, что показывает `systemctl is-active`.

**Ещё одна проверка.** Откройте `journalctl -u xray-fedarisha -n 200` и
убедитесь, что нет `panic:`. Ветка C1 (падение процесса на коротком имени
сессии) как раз давала панику.

## Откат

Скрипт откатывается сам при любой неудаче. Вручную — одна команда, путь
подскажет вывод скрипта:

```bash
systemctl stop xray-fedarisha
cp -a /usr/local/bin/xray-fedarisha.bak.<метка> /usr/local/bin/xray-fedarisha
systemctl start xray-fedarisha
```

Посмотреть, что есть:

```bash
ls -lt /usr/local/bin/xray-fedarisha.bak.*
```

## Если пошло не так

**`systemctl is-active` зелёный, а туннель не работает.** Сервер может быть
жив, а бакет отдавать ошибки. Смотреть журнал:

```bash
journalctl -u xray-fedarisha -n 100 --no-pager
```

Новые строки, которые стоит увидеть при проблемах:

- `read list failed (retrying)` — бакет отдаёт ошибку на `List`. Раньше эта
  ошибка была полностью проглочена, поэтому причину находили только
  предположительно;
- `delete queue full` — housekeeping не успевает и сбрасывает часть удалений.
  Это безопасно: на `Close` всё подчищается;
- `cleanup: giving up on <каталог>` — сессия осталась в бакете. Раньше этот
  случай был неотличим от штатной уборки в логе.

**`run -test` отверг конфиг.** Значит новый бинарь не понимает текущий
конфиг. Ничего не сломано — работающий сервер не тронут, скрипт остановился
до подмены. Пришлите вывод, разберёмся.

**SHA-256 не совпал.** Так и должно быть. Ничего не ставится.

## Про осиротевшие каталоги

В бакете осталось около 60 старых сессионных каталогов от упавших клиентов.
Обновление **уже** перестаёт их опрашивать — это был один из симптомов, а не
побочный эффект. Но сами объекты продолжают занимать место.

Чистить их — отдельная операция, и она рискованная: удаление не того префикса
уронит живые сессии. В репозитории есть `tools/prefixtool` для точечной
работы. Отдельно и только после того, как обновление встало и проверено.
